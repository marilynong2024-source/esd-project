 3. BUSINESS SCENARIO & “INTERESTING” FLOWS
================================================================================

  Brand: Horizon Packages — bundled flight + hotel booking.

  Flow A — Search & price bundle:
    User picks origin/destination/dates/travellers; UI calls bundle-pricing
    which calls flight, hotel, discount, loyalty (coins preview), returns
    breakdown and final total.

  Flow B — Book package:
    Holds seat + room, optional loyalty redeem, simulated payment, confirms
    inventory, earns loyalty, synchronous notify/manual + AMQP notify.user
    (SMS/email side effects in notification service).

  Flow C — Cancel:
    Refund via payment service, release seat/room, restore availability counts,
    loyalty reversal, AMQP + synchronous notify/manual, optional SMS.

  Assumptions to state in report:
    SGD currency in UI demo; simplified airline/hotel inventory; payment is not
    a live card processor unless you wire one yourself.

 4. ARCHITECTURE OVERVIEW
================================================================================

  Browser → nginx (ui service) serves static files and reverse-proxies /api/*
  to internal containers by DNS name on the Docker network.

  booking service is the main COMPOSITE for create/cancel: it calls account,
  flight, hotel, payment, loyalty, notification HTTP, and publishes to
  RabbitMQ.

  notification service consumes AMQP from exchange travel_topic, queue bound to
  routing keys notify.user and booking.cancelled (bindings in code), appends
  events to in-memory list; Twilio SMS if configured.

  graphql_gateway aggregates flight/hotel/loyalty for BTL-style queries.

  kong is included for gateway BTL demos; primary student path is often
  localhost:8080 (nginx), not Kong ports.

11. END-TO-END: CREATE BOOKING (ORCHESTRATION)
================================================================================

  UI: POST /api/booking/booking  (JSON body with customerID, flightID, hotelID,
       totalPrice, departureTime, traveller profile ids, coins, etc.)

  Diagram aliases (same handler):
    POST /book-package
    POST /booking

  High-level server steps (booking/app.py):
    1. Validate payload; optional catalog validation flight+hotel
    2. GET http://account:5100/account/{customerID}
       - 404 → fail; non-Active → 403; unreachable → warning only
    3. Validate traveller profiles (OutSystems or local fallback per code)
    4. Persist booking row (status PENDING)
    5. POST flight: reserve-seat
    6. POST hotel: hold-room
    7. GET loyalty points; optional POST redeem (pre-pay coins)
    8. POST payment: .../payment/process
    9. PUT flight: confirm-seat ; PUT hotel: confirm-room
   10. PUT flight: /availability/{seat}/CONFIRMED (inventory)
       PUT hotel: /availability/{hotelID}/CONFIRMED (inventory)
   11. Set booking CONFIRMED in DB
   12. POST loyalty .../earn (post-payment rewards)
   13. POST notification /notify/manual (sync confirmation payload)
   14. AMQP publish routing_key notify.user with rich payload (email, phone...)

  Failure before pay: release-seat and release-room rollback pattern.

================================================================================
12. END-TO-END: CANCEL BOOKING
================================================================================

  UI: POST /api/booking/booking/cancel/{id}  with JSON body cancelSource

  Diagram alias:
    POST /cancel-booking  body: { bookingID, userID?, cancelSource? }
    userID optional check against booking.customerID

  Steps:
    1. Compute refund % and amount from policy (fare, tier, days, source)
    2. POST payment .../refund-payment  { bookingID, refundAmount }
    3. PUT flight .../flight/inventory/{seat}/release
    4. PUT hotel .../hotel/inventory/{room}/release
    5. PUT availability .../RELEASED (restore seat/room counts)
    6. Update booking row CANCELLED + refund fields
    7. POST loyalty .../refund (reversal — not the same as /redeem)
    8. AMQP notify.user with cancellation payload
    9. POST notification /notify/manual (sync fallback)

--------------------------------------------------------------------------------
II-A  RABBITMQ — WHAT IT DOES HERE
--------------------------------------------------------------------------------

  Role:
    Asynchronous messaging between the booking composite and the notification
    service. Booking does NOT call notification for the AMQP path; it only
    PUBLISHES. Notification SUBSCRIBES — that is message-driven “choreography”.

  Where it runs:
    docker-compose service `rabbitmq` (image rabbitmq:3-management).
    Host ports (to avoid clashing with other stacks):
      AMQP:   5674 → container 5672
      UI:     15673 → container 15672 (management plugin)
    Default user/pass in compose: guest / guest

  Topology (as code declares it):
    Exchange:  travel_topic
    Type:      topic
    Durable:   yes (survives broker restart; messages still need persistence flag)

    Producer (booking/app.py):
      Uses library `pika`.
      Connects using RABBIT_HOST / RABBIT_PORT from environment (in Docker:
      rabbitmq and 5672).
      Declares the same exchange name/type before publish.
      Publishes JSON body with routing_key **notify.user** for BOTH:
        - successful booking confirmation (after pay/confirm)
        - cancellation (after refund/release)
      Message properties: delivery_mode=2 (persistent) where implemented.

    Consumer (notification/app.py):
      Starts a **background daemon thread** when Flask starts (with a guard so
      Flask debug reloader does not double-start the consumer).
      Connects with pika.BlockingConnection.
      Declares exchange `travel_topic` (topic, durable).
      Declares queue name from env **QUEUE_NAME** (compose sets `notify.user`).
      Binds queue to exchange for routing keys:
        - notify.user
        - booking.cancelled
      (Booking currently publishes notify.user; extra bind keeps lab/diagram
      compatibility if you add booking.cancelled publishes later.)

    Per-message callback:
      1. Parses JSON payload (or stores raw string on failure).
      2. Appends an entry to in-memory NOTIFICATIONS list (source: "amqp").
      3. Calls Twilio SMS helper (twilio_integration.py) using payload fields
         like passengerPhone, bookingID, confirmedAt vs cancelledAt.
      4. Acknowledges the message (basic_ack) so it is removed from the queue.

  Why RabbitMQ for the course story:
    - Satisfies “message-based communication between microservices”.
    - Shows **decoupling**: booking can complete even if notification is slow;
      messages queue until the consumer processes them.
    - Demo tip: open RabbitMQ management UI during presentation to show the
      broker, or show GET /api/notification/notifications after a booking.

--------------------------------------------------------------------------------
II-B  KONG — WHAT IT DOES HERE
--------------------------------------------------------------------------------

  Role:
    API **gateway** in front of the same Flask microservices — an optional
    **second entry point** for Beyond-The-Labs / SOA diagrams. The main web UI
    does NOT go through Kong by default; the browser talks to **nginx** on
    port 8080.

  Where it runs:
    docker-compose service `kong` (image kong:latest).
    Declarative mode: **no separate Kong database** (KONG_DATABASE: off).
    Config file mounted read-only: ./kong.yml → /kong/declarative/kong.yml

  Host ports (from compose):
    9000 → Kong proxy (HTTP)
    9001 → Kong admin API
    (Also 9443/9444 for TLS variants — see compose comments.)

  How kong.yml is structured:
    Each `service` has:
      - `name` (logical name)
      - `url`  (upstream base, e.g. http://booking:5101)
      - `routes` with `paths` such as /account, /booking, /flight, /hotel,
        /payment, /loyalty, /notification, /graphql, /bundle-pricing, /discount
      - `strip_path: false` — the path the client sends is passed through to
        the upstream as-is (important: Flask routes include prefixes like /booking).

  Example client call:
    POST http://localhost:9000/booking/booking
    → Kong forwards to http://booking:5101/booking/booking

  Relationship to nginx:
    nginx adds a **single** browser origin (localhost:8080) and prefixes like
    /api/booking/... then **rewrites** to strip the prefix before the upstream.
    Kong exposes **service paths without** that /api/ prefix. Both patterns are
    valid; document which one your demo uses.

  Report angle:
    “We use Kong as a dedicated API gateway layer for routing to microservices,
    complementing nginx which acts as static file server + BFF-style proxy for
    the web UI.”

--------------------------------------------------------------------------------
II-C  GRAPHQL — WHAT IT DOES HERE
--------------------------------------------------------------------------------

  Role:
    **Beyond-the-labs** API style: one POST endpoint that can return **shaped**
    data from **multiple** REST microservices in one round-trip. REST remains
    the primary inter-service protocol; GraphQL is an **aggregation facade** for
    the client (or for demos).

  Service:
    `graphql_gateway` — Flask app in graphql_gateway/app.py, port 5110.

  Stack:
    - `graphene` schema defines types: Hotel, Flight, Loyalty, PackagePreview.
    - Resolvers use `requests.get` to call existing REST APIs on the Docker network:
        FLIGHT_BASE  = http://flight:5102/flight
        HOTEL_BASE   = http://hotel:5103/hotel
        LOYALTY_BASE = http://loyalty:5105/loyalty

  Exposed HTTP:
    GET  /              health JSON pointing to /graphql
    POST /graphql       body: { "query": "...", "variables": { ... } }

  Implemented operations (schema):
    - hotelSearch(country, city, name) → list of hotels with roomTypes, etc.
      Resolver calls HOTEL_BASE/search with query params.
    - packagePreview(customerID, flightID, hotelID, roomCode) → combines
      GET flight/{flightNum}, GET hotel/{id}, GET loyalty/{id}/points and
      computes a simple estimated total (flight economy + first/chosen room).

  How the browser reaches it:
    nginx location /api/graphql/ rewrites to the graphql container path.
    UI typically POSTs to: /api/graphql/graphql
    (rewrite strips /api/graphql prefix so upstream sees /graphql.)

  Course justification (short):
    “Reduces multiple REST calls for search/preview screens; lets the client
    request only the fields it needs; demonstrates polyglot integration without
    breaking microservice ownership (GraphQL service is stateless and calls
    atomic REST services).”

--------------------------------------------------------------------------------
II-D  NGINX (ui SERVICE) — WHAT IT DOES HERE
--------------------------------------------------------------------------------

  Role:
    1) Serve the static web app (index.html, app.js, styles.css) from /usr/share/nginx/html
    2) Reverse-proxy **API** calls so the browser stays on **same origin**
       http://localhost:8080 — avoids CORS pain and mixed ports in production-like demos.

  Implementation:
    docker-compose `ui` service uses **official image** `nginx:alpine` — there is
    **no Dockerfile** in the repo for the UI; only a bind mount:
      ./ui           → /usr/share/nginx/html (read-only)
      ./nginx/ui.conf → /etc/nginx/conf.d/default.conf (read-only)

  Resolver:
    `resolver 127.0.0.11` — Docker’s embedded DNS so upstream hostnames like
    `booking` resolve when nginx starts.

  Location blocks (summary):
    /api/booking/*      → http://booking:5101  with rewrite to drop /api/booking/
    /api/loyalty/*      → loyalty:5105
    /api/notification/* → notification:5106
    /api/flight/*       → flight:5102
    /api/hotel/*        → hotel:5103
    /api/graphql/*      → graphql:5110
    /api/discount/*     → discount:5112
    /api/bundle-price   → bundle-pricing:5111  (special rewrite to /bundle-price)
    /                   → try_files for SPA-style static hosting

  Headers:
    proxy_set_header Host, X-Real-IP, X-Forwarded-For, X-Forwarded-Proto as needed.

  Why this matters:
    The UI JavaScript uses relative paths like `/api/booking/...` — no hard-coded
    :5101 ports in the browser.

II-E  OUTSYSTEMS — WHAT IT DOES HERE
--------------------------------------------------------------------------------

  Role:
    Satisfies the course requirement: **at least one atomic service built/exposed
    on OutSystems**. In this project, the **Traveller Profile** domain is owned
    by OutSystems (REST API). The **booking** microservice (Python) is the
    **client** that calls OutSystems over HTTPS.

  Code locations:
    - travellerprofile/outsystems_client.py — HTTP wrapper (Create, byaccount,
      Update, Delete) with env-configurable base URL and path names.
    - booking/traveller_os.py — validation and orchestration helpers used from
      booking/app.py when creating bookings and managing traveller CRUD routes.
    - booking/Dockerfile copies outsystems_client.py into the image as
      traveller_outsystems_client.py for import stability inside the container.

  Configuration (.env / compose env on booking):
    TRAVELLER_PROFILE_BASE_URL   — OutSystems REST base URL (no trailing slash)
    TRAVELLER_PROFILE_REQUIRED   — if true and URL set, invalid/missing profiles
                                   can fail booking creation
    TRAVELLER_PROFILE_UPDATE_PATH / TRAVELLER_PROFILE_DELETE_PATH — REST action
                                   segment names if your OS module differs

  Typical REST shapes:
    POST .../CreateTravellerProfile with JSON body (CustomerID, FullName,
      PassportNumber, etc.)
    GET  .../byaccount/{customerID} for listing profiles for a member

  Operational notes:
    - OutSystems runs **outside** Docker Compose; booking container must reach
      the internet or a tunnel to hit the OS cloud URL.
    - If URL is empty/unset, behaviour falls back according to booking code paths
      (demo-friendly degradation — confirm in traveller_os.py for exact rules).

  Report / demo:
    Show one create + list + use profile on booking; include OS module screen
    shot or link in appendix if allowed.

II-F  EVERY DOCKERFILE IN THIS REPO (LINE-BY-LINE PURPOSE)
--------------------------------------------------------------------------------

  Common pattern:
    All **Python** services use `FROM python:3.11-slim`, `WORKDIR /app`,
    copy only needed sources, `pip install` minimal deps, `EXPOSE` port,
    `CMD ["python", "app.py"]`. This keeps images small and build fast.

  booking/Dockerfile
    - FROM python:3.11-slim
    - WORKDIR /app
    - COPY booking/*.py (app, traveller_os, fx_quote, catalog_validate)
    - COPY travellerprofile/outsystems_client.py → traveller_outsystems_client.py
    - pip: flask, flask-cors, requests, flask_sqlalchemy, pymysql, pika
      (pika = RabbitMQ publisher; pymysql = MySQL driver)
    - EXPOSE 5101
    - CMD python app.py
    Build context: **project root** (see compose `context: .` dockerfile: booking/Dockerfile)

  flight/Dockerfile
    - Single app.py, flask + flask-cors only
    - EXPOSE 5102

  hotel/Dockerfile
    - Same pattern as flight
    - EXPOSE 5103

  payment/Dockerfile
    - Same minimal Flask pattern
    - EXPOSE 5104

  loyalty/Dockerfile
    - Same minimal Flask pattern
    - EXPOSE 5105

  account/Dockerfile
    - Same minimal Flask pattern
    - EXPOSE 5100

  notification/Dockerfile
    - COPY app.py, smu_integration.py, twilio_integration.py
    - RUN mkdir -p /app/data  (writable dir for Twilio JSON when volume mounted)
    - pip: flask, flask-cors, pika, requests, twilio
    - EXPOSE 5106

  graphql_gateway/Dockerfile
    - COPY app.py only
    - pip: flask, flask-cors, requests, graphene
    - EXPOSE 5110

  bundle_pricing/Dockerfile
    - COPY app.py; pip: flask, flask-cors, requests
    - EXPOSE 5111

  discount/Dockerfile
    - COPY app.py; pip: flask, flask-cors, requests
    - EXPOSE 5112

  What does **NOT** have a Dockerfile in-repo:
    - **ui** — uses `image: nginx:alpine` + volume mounts (see II-D).
    - **rabbitmq** — uses official `rabbitmq:3-management` image.
    - **booking-db** — uses official `mysql:8.0` image.
    - **kong** — uses official `kong:latest` image.

  docker-compose.yml ties images together:
    - build: ./service for custom Dockerfiles
    - image: for third-party images
    - depends_on: startup order (not full health on all services — booking waits
      on booking-db healthy)
    - volumes: e.g. notification_twilio_data for Twilio config persistence
    - env_file / environment: inject .env and literals

III-A  SEARCH & PRICE BUNDLE (Bundle Pricing composite diagram)

  Diagram intent:

        3) GET http://hotel:5103/availability     (city, room type, dates)
        4) GET http://hotel:5103/hotels/price     (alias of /price)
        5) GET http://discount:5112/discounts/bundle-rule  (alias of /discount-rule)
        6) GET http://loyalty:5105/loyalty/{cid}/points  (for loyaltyUsed / coins)

  Diagram vs demo DBs:
    The figure shows separate FlightDB, HotelDB, DiscountDB tables. In the repo,
    flight/hotel/discount use **in-memory** Python structures for the demo; only

III-B  BOOK PACKAGE (Composite diagram — happy path)
--------------------------------------------------------------------------------

  Diagram steps (typical numbering) → our code (booking/app.py create_booking):

  1) UI POST {userID, flightID, hotelID, travellerDetails, …}
     → POST /api/booking/booking  (same handler as POST /book-package on booking)

  2) Customer account check
     → GET http://account:5100/account/{customerID}
     → Strict: 404 / inactive account fails or blocks per current code paths.

  3) Traveller profile
     → OutSystems REST via traveller_os + outsystems_client (not a separate
     Docker service). Maps to “TravellerDB” in the diagram.

  4) Reserve seat
     → POST http://flight:5102/reserve-seat  (JSON bookingID, flightNum, seatNo, …)

  5) Hold room
     → POST http://hotel:5103/hold-room

  6) Loyalty points + redeem before payment
     → GET …/loyalty/{id}/points
     → POST …/loyalty/{id}/redeem  (coins for discount)

  7) Payment external API
     → POST http://payment:5104/payment/process
     → **Simulated** in-repo (not live Stripe). Say “Stripe-shaped external PSP
     microservice” in the report if you align wording with the diagram.

  8–11) After successful payment
     → PUT flight confirm-seat, PUT hotel confirm-room
     → PUT …/availability/{seat}/CONFIRMED and PUT …/availability/{hotelID}/CONFIRMED
       (inventory adjustment on in-memory catalog — diagram “update availability”)

  12) Notification
     → POST http://notification:5106/notify/manual  (sync confirmation payload)
     → AMQP publish routing_key **notify.user** with email, phone, bookingID, etc.

  13) Loyalty earn
     → POST …/loyalty/{id}/earn  (post-payment rewards / tier)

  14–15) Response to UI
     → JSON { code, data: booking.to_dict(), … }  (booking id = confirmation ref)

  Saga / rollback (not on diagram):
     If payment fails, booking calls release-seat and release-room. Mention in
     report as compensating actions.

III-C  CANCELLATION & REFUND (Cancellation diagram)
--------------------------------------------------------------------------------

  1) UI cancel {bookingID, userID}
     → POST /api/booking/booking/cancel/{id}  or  POST /api/booking/cancel-booking

  2–3) Refund payment
     → POST …/refund-payment  (or /payment/refund-payment) with bookingID and
     refundAmount. **paymentRef** is not required by our simulated payment service
     but can be added in a future iteration — note if instructors ask.

  4–5) Release seat
     → Diagram: PUT /release-seat {flightRef}
     → We call PUT …/flight/inventory/{seatNo}/release with bookingID + flightNum,
       and flight **release-seat** also accepts **flightRef** in JSON for parity.

  6–7) Release room
     → Diagram: PUT /release-room/{id} {hotelRef}
     → We call PUT …/hotel/inventory/{roomId}/release (composite room id).

  8–9) Loyalty reversal (IMPORTANT — wording differs from diagram)
     → Diagram often shows POST /loyalty/{customerID}/redeem for cancellation.
     → Our implementation uses POST /loyalty/{customerID}/ **refund** with a JSON
       body that reverses earned points and restores spent coins — **clearer
       semantics** than overloading “redeem”. In the report: *“We implement the
       diagram’s loyalty reversal using a dedicated /refund endpoint.”*

  10) AMQP cancellation event
     → Publish **notify.user** with cancelledAt, refundAmount, email, phone, …

  11) Sync cancellation notice
     → POST /notify/manual  (fallback / parallel path in our code)

  12) UI result {status, refundAmt}
     → HTTP 200 JSON with data.status CANCELLED and refund fields.

  Extra step in code:
     → PUT /availability/.../RELEASED on flight and hotel to restore **seat/room
     counts** in the demo catalog after cancel.
