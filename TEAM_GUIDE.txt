 3. BUSINESS SCENARIO & “INTERESTING” FLOWS
================================================================================

  Brand: Horizon Packages — bundled flight + hotel booking.

  Flow A — Search & price bundle:
    User picks origin/destination/dates/travellers; UI calls bundle-pricing
    which calls flight, hotel, discount, loyalty (coins preview), returns
    breakdown and final total.

  Flow B — Book package:
    Holds seat + room, optional loyalty redeem, simulated payment, confirms
    inventory, earns loyalty, synchronous notify/manual + AMQP notify.user
    (SMS/email side effects in notification service).

  Flow C — Cancel:
    Refund via payment service, release seat/room, restore availability counts,
    loyalty reversal, AMQP + synchronous notify/manual, optional SMS.

  Assumptions to state in report:
    SGD currency in UI demo; simplified airline/hotel inventory; payment is not
    a live card processor unless you wire one yourself.

 4. ARCHITECTURE OVERVIEW
================================================================================

  Browser → nginx (ui service) serves static files and reverse-proxies /api/*
  to internal containers by DNS name on the Docker network.

  booking service is the main COMPOSITE for create/cancel: it calls account,
  flight, hotel, payment, loyalty, notification HTTP, and publishes to
  RabbitMQ.

  notification service consumes AMQP from exchange travel_topic, queue bound to
  routing keys notify.user and booking.cancelled (bindings in code), appends
  events to in-memory list, optional Twilio/SMU.

  graphql_gateway aggregates flight/hotel/loyalty for BTL-style queries.

  kong is included for gateway BTL demos; primary student path is often
  localhost:8080 (nginx), not Kong ports.

 8. ENVIRONMENT VARIABLES (.env)
================================================================================

  Compose loads .env for substitution on services that declare env_file: .env
  (e.g. booking). Do NOT commit real secrets.

  Booking-related:
    BOOKING_DB_URL       MySQL URL for SQLAlchemy
    TRAVELLER_PROFILE_BASE_URL   OutSystems REST base (empty = optional OS)
    TRAVELLER_PROFILE_REQUIRED   true = strict validation when URL set
    TRAVELLER_PROFILE_UPDATE_PATH / DELETE_PATH  OS action names
    SKIP_CATALOG_VALIDATION      skip flight/hotel existence checks if true
    FX_API_ENABLED / FX_API_URL  optional FX snippet on booking response

  SMU email (notification service — add under notification.environment in
  compose if you removed env_file; or use compose environment block):
    SMU_NOTIFICATION_ENABLED, BASE_URL, SMU_NOTIFY_EMAIL_TO, AUTH header/value

  Twilio:
    Legacy TWILIO_* env vars are NOT required for notification: Twilio is
    configured via UI POST /api/notification/twilio/config and persists under
    Docker volume notification_twilio_data → /app/data.

  Booking → Notification HTTP:
    NOTIFICATION_URL=http://notification:5106  (set in compose for booking)

11. END-TO-END: CREATE BOOKING (ORCHESTRATION)
================================================================================

  UI: POST /api/booking/booking  (JSON body with customerID, flightID, hotelID,
       totalPrice, departureTime, traveller profile ids, coins, etc.)

  Diagram aliases (same handler):
    POST /book-package
    POST /booking

  High-level server steps (booking/app.py):
    1. Validate payload; optional catalog validation flight+hotel
    2. GET http://account:5100/account/{customerID}
       - 404 → fail; non-Active → 403; unreachable → warning only
    3. Validate traveller profiles (OutSystems or local fallback per code)
    4. Persist booking row (status PENDING)
    5. POST flight: reserve-seat
    6. POST hotel: hold-room
    7. GET loyalty points; optional POST redeem (pre-pay coins)
    8. POST payment: .../payment/process
    9. PUT flight: confirm-seat ; PUT hotel: confirm-room
   10. PUT flight: /availability/{seat}/CONFIRMED (inventory)
       PUT hotel: /availability/{hotelID}/CONFIRMED (inventory)
   11. Set booking CONFIRMED in DB
   12. POST loyalty .../earn (post-payment rewards)
   13. POST notification /notify/manual (sync confirmation payload)
   14. AMQP publish routing_key notify.user with rich payload (email, phone...)

  Failure before pay: release-seat and release-room rollback pattern.

================================================================================
12. END-TO-END: CANCEL BOOKING
================================================================================

  UI: POST /api/booking/booking/cancel/{id}  with JSON body cancelSource

  Diagram alias:
    POST /cancel-booking  body: { bookingID, userID?, cancelSource? }
    userID optional check against booking.customerID

  Steps:
    1. Compute refund % and amount from policy (fare, tier, days, source)
    2. POST payment .../refund-payment  { bookingID, refundAmount }
    3. PUT flight .../flight/inventory/{seat}/release
    4. PUT hotel .../hotel/inventory/{room}/release
    5. PUT availability .../RELEASED (restore seat/room counts)
    6. Update booking row CANCELLED + refund fields
    7. POST loyalty .../refund (reversal — not the same as /redeem)
    8. AMQP notify.user with cancellation payload
    9. POST notification /notify/manual (sync fallback)

13. BUNDLE PRICING COMPOSITE
================================================================================

  Endpoint (via nginx):
    GET /api/bundle-price?origin=&destination=&departDate=&returnDate=
        &numberOfTravellers=&customerId=&roomType=&loyaltyCoinsToUseCents=

  Internal calls (bundle_pricing/app.py):
    - GET flight /availability then GET flight /flights/price (alias of /price)
    - GET hotel /availability then GET hotel /hotels/price
    - GET discount /discounts/bundle-rule (alias of /discount-rule)
    - Optional GET loyalty /{id}/points for coin preview

  Response data includes flightPrice, hotelPrice, discount, loyaltyUsed,
  finalTotal, plus helper fields (flightNum, hotelID, discountPercent, ...).

14. DISCOUNT RULES (CURRENT BEHAVIOUR)
================================================================================

  discount/app.py:
    - Endpoints: GET /discount-rule  AND  GET /discounts/bundle-rule
    - Baseline: 10% bundle discount when tier/bundle rules do not yield higher
    - Stricter tier rules apply when travellers>=2, nights>=3, room DLX, and
      loyalty tier matches; highest eligible percent wins (min 10%).

  Report should describe this accurately (do not claim “always 0%”).

17. NOTIFICATION: RABBITMQ, TWILIO, SMU
================================================================================

    GET  /notifications
    POST /notify/manual
    GET  /twilio/config
    POST /twilio/config

25. TROUBLESHOOTING
================================================================================

  Blank UI / failed fetches:
    - Confirm URL is localhost:8080 not file://
    - docker compose ps — ui, booking, booking-db healthy

  Booking 500 / DB errors:
    - docker compose logs booking-db, booking
    - Verify BOOKING_DB_URL matches compose DB credentials

  Notifications empty:
    - rabbitmq up; notification logs “Waiting for AMQP”
    - booking logs “Published AMQP notify.user”

  Twilio skipped:
    - Enable checkbox + save SID/token/from in UI
    - Trial: verify destination number in Twilio console
    - Phone on form must normalize to E.164 (SG defaults in code)

  GraphQL errors:
    - graphql container up; path /api/graphql/graphql double “graphql” is correct

29. FAQ
================================================================================

  Q: Do we need real Stripe?
  A: No. Course wants an external service; Twilio (or SMU) suffices. Say payment
     is simulated unless you integrate real Stripe test mode.

  Q: Is MySQL mandatory?
  A: Course wants ≥1 DB; not necessarily MySQL. This repo uses MySQL for
     booking — that satisfies the requirement.

  Q: What if OutSystems is down?
  A: Have TRAVELLER_PROFILE_BASE_URL empty for local-only demo OR video backup
     with tunnel working; explain in report.

  Q: Where is the “booking reference” for cancel?
  A: Shown in right-hand summary JSON after successful create (booking id).
